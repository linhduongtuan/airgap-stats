I

Orientation

What this codebase is, why it's built the way it is, and how the pieces fit together before you read any code.

What this codebase is

AirGap Stats is a toolkit for doing statistical analysis with an AI coding agent (Claude, or any similar tool) without the real dataset ever reaching the agent. The user keeps their real data on their own machine, outside the repo; the agent only ever sees a structural description of it (variable names, types, a handful of category labels) and a fully synthetic stand-in dataset it generates itself. Every script the agent writes is developed and verified against that synthetic file. Only the human ever runs the finished script against the real data, in their own RStudio or Python session — the agent never touches real values, real row counts, or real statistics at any point. The name is literal: the real dataset is air-gapped from the AI at every stage, the same way a secure system is air-gapped from a network.

A quick note on naming: skill and file names throughout this repo keep the dr- prefix (dr-00-privacy-gate, dr_workflow_state.yaml, and so on) — those are functional identifiers referenced by skill discovery, mirror-sync tooling, and every skill doc's own cross-references, not the product's brand name, so they stay as-is regardless of what the project is branded.

This document is superseded

This Python-only guide predates the full bilingual rewrite. See docs/codebase-tutorial.html for the current, maintained version covering both Python and R — it supersedes everything here.

Two analysis tracks are supported, each with its own set of statistical methods (Part III covers both in depth):

  • Medical — crude/adjusted logistic regression, confounder adjustment, survival analysis, propensity-score methods. Used by crp-mortality and example-clinical.
  • SEM — confirmatory factor analysis, structural/mediation models on Likert-scale survey items. Used by burnout-mediation and example-survey-sem.

Every project moves through the same five stages, labeled A through E. This is the mental model to hold onto before reading any script — almost every file in this repo exists to serve exactly one of these stages.

Why this matters for reading the code

When you see a script's USER SETTINGS block default to data_synthetic/synthetic_dataset.csv, that's Stage D. When a script requires an input() prompt or a real file path with no default, that's Stage A/B/C — it structurally cannot run without a human supplying real data, by design.

The privacy model, in code

The privacy guarantee isn't a policy statement — it's enforced by what the code physically does and does not read or write. Three mechanisms, from the actual source:

  1. Real data never gets a persisted variable. Every generic template that touches real data (py-scripts/pattern_extract.py, py-scripts/synthesize_data.py, py-scripts/synthesize_data_correlated.py) takes it as an in-memory data: pd.DataFrame argument the caller supplies at runtime, computes only aggregate structure from it (a range, a correlation matrix, a set of category labels), and never writes that structure to any file — only the synthetic output gets written.
  2. The exported pattern file is a strict allowlist. extract_pattern() in pattern_extract.py only ever writes six columns: variable, type, levels, n_distinct, missing_pct, note. Rare category levels get masked to "Other" before export, and n_distinct itself is withheld (set to None) for any type where it would leak the real row count or bound it. There is no code path that writes a raw value, a row count, or a summary statistic into the pattern file.
  3. Formula-injection and magic-byte safety nets exist even for the synthetic/derived files the agent does handle, consistent with the same defense-in-depth posture — belt-and-suspenders even where the primary guarantee (real data never enters the process) already holds.

Repository architecture

Ignoring the R mirror (each Python piece below has a base-R equivalent, documented in that script's own header), the Python-relevant layout is:

py-scripts/ # generic, per-track templates -- copied into a project and adapted pattern_extract.py # Stage A synthesize_data.py # Stage B synthesize_data_correlated.py # Stage B2 (opt-in) desc.py, plots.py # Stage D2 (descriptive) infer.py # Stage D3/D4 medical track sem_measurement.py, sem_structural.py, plots_sem.py # Stage D3/D4 SEM track tools/ # the actual statistical-methods packages -- imported by project scripts sap_gate/ # Phase 0: pre-registration QA gate diagnostics/ # Phase 1: VIF, influence, bootstrap validation, group tests medical_track/ # Phase 2: Firth regression, survival, PSM, multiplicity sem_track/ # Phase 3: ordinal CFA, reliability, validity, mediation, invariance reporting/ # Phase 5: auto-extraction for Stage E manuscript output smoke_test.py, parity_check.py, skills_sync_check.py # Phase 6: maintainer tooling projects/ # one folder per research question crp-mortality/ # medical track: CRP -> 30-day mortality example-clinical/ # medical track: treatment -> mortality burnout-mediation/ # SEM track: job satisfaction -> burnout -> turnover (mediation) example-survey-sem/ # SEM track: burnout/satisfaction -> turnover (parallel) _template/ # empty starting point for a new project <project>/scripts/ # the actual, adapted-per-project copies that get run <project>/pattern/, data_synthetic/, outputs_synthetic/, plans/, results_real/ tests/ # one self-contained test_*.py per tools/ package, no pytest skills/ # the agent-facing instructions that drive each DR stage (Markdown, not Python)

The important relationship to internalize: py-scripts/ holds generic templates and tools/ holds the actual statistical logic as importable functions; a project's own scripts/*.py files are adapted copies that hardcode that project's variable names and call into tools/ for anything non-trivial. When you fix a bug in a statistical method, you fix it once in tools/ — the project scripts that import it pick up the fix automatically.

The generic templates in py-scripts/ do not get the same automatic benefit — copying a template into a project is a one-time snapshot, not a living link. Part IV documents this precisely, including a gap that existed until 2026-08-16 (the templates had fallen behind the four example projects) and how it was closed.

Installing & running

The whole Python side runs from one virtual environment at the repo root, managed with uv:

terminalbash
# one-time setup, from the repo root
uv venv
uv pip install -e .

# every project script is run FROM THE PROJECT FOLDER, not the repo root --
# this is a hard convention throughout the codebase (relative paths assume it)
cd projects/crp-mortality
../../.venv/bin/python scripts/desc.py
../../.venv/bin/python scripts/infer.py

pyproject.toml pins the dependency list: pandas, numpy, matplotlib, statsmodels, semopy, pyyaml, scipy, patsy. Nothing in tools/ or py-scripts/ needs anything beyond that list — no scikit-learn, no extra SEM packages.

Every project script assumes it's run from that project's folder

Paths like "data_synthetic/synthetic_dataset.csv" in a script's USER SETTINGS block are relative to the current working directory, which every script's own header comment states explicitly ("Run from the project folder"). Running a script from the repo root instead is the single most common way to hit a spurious FileNotFoundError when working in this codebase.

Follows projects/crp-mortality — a medical-track project asking whether CRP (C-reactive protein) is associated with 30-day mortality — through every Python script, in the order they actually run. Read this section top to bottom the first time; come back to Part III for the full reference on any function mentioned along the way.

  2. Synthesize data — py-scripts/synthesize_data.py

    synthesize_data() reads the reviewed pattern file and, for every row, generates n fabricated values matching that column's type. It optionally accepts the real data too — used only, locally, at runtime, to pick a plausible numeric range (e.g. age's min/max) so the synthetic column doesn't look absurd; that range is never written anywhere.

    py-scripts/synthesize_data.pypython
    def _gen_column(col_type, levs, nm, n, rng, data):
    if col_type == "binary":
        vals = levs if levs else ["0", "1"]
        return rng.choice(vals, size=n)
    elif col_type == "numeric":
        lo, hi = _local_range(data, nm, 0, 100)
        return np.round(rng.uniform(lo, hi, size=n), 2)
    # ... integer, integer_scale, categorical, id_like, date follow the same pattern

    Every column is generated independently of every other column — that's a deliberate safety margin, not an oversight, so no real relationship between variables can leak into the file. The cost: a model fit on this file has nothing real to converge to, so Stage D scripts explicitly document that a degenerate fit on synthetic data is expected. If you need to check that a model actually converges under realistic correlation, Stage B2 below is the opt-in alternative.

    Stage B2: correlated synthesis (optional)

    py-scripts/synthesize_data_correlated.py is the same contract, extended: it computes the real data's pairwise Spearman correlation matrix locally, projects it to the nearest valid correlation matrix, and generates synthetic rows via a Gaussian copula (Cholesky decomposition → standard normal draws → inverse-transform through each variable's own empirical marginal) so the synthetic file preserves approximate real correlation — still with zero real rows copied. It requires data (raises if None) since there is nothing to correlate without it. See Part III's repo tooling section, or the file's own extensive docstring, for the full privacy design.

  3. Descriptive analysis — scripts/desc.py

    Builds a Table 1 (baseline characteristics by outcome group) with a formally chosen test per row — not just a mean and a p-value from whatever test happened to be habitual:

    projects/crp-mortality/scripts/desc.pypython
    from tools.diagnostics import compare_categorical, compare_continuous

group_var        = "mortality_30day"
continuous_vars   = ["age", "bmi", "sbp", "egfr", "hba1c", "crp"]
categorical_vars  = ["sex", "treatment", "diabetes", "hypertension", "smoking", "complication"]

    result = compare_continuous(dat, var, group_var)   # picks Welch t / ANOVA / Mann-Whitney / Kruskal at runtime
    # result.test_used, result.p_value, result.branch_reason all get logged

    compare_continuous (from tools.diagnostics.group_tests, detailed in Part III) runs a Shapiro-Wilk normality check per group first, then branches: both groups normal → Welch's t-test (2 groups) or Welch's ANOVA (>2); otherwise Mann-Whitney U or Kruskal-Wallis. The choice and its reason are recorded, never assumed in advance, because nobody — not the agent, not the SAP author — has seen the real data's distribution yet.

    Why Firth's method is hand-implemented, not imported

    No maintained Python package implements Firth's penalized logistic regression. tools/medical_track/firth_logistic.py hand-rolls the modified-score IRLS algorithm (Firth 1993; Heinze & Schemper 2002) and was cross-validated against R's logistf package during development — agreement to 4+ decimal places on both a well-behaved dataset and a deliberately-separated one (see Part III).

  5. Survival & propensity-score sensitivity — scripts/survival.py, scripts/psm.py

    Two extension scripts, both new in Phase 2, that exist because a single crude+adjusted logistic regression leaves real information and real robustness questions on the table:

    • survival.py — length_of_stay sits unused in the base analysis; dichotomizing the outcome at a fixed 30-day window throws away exactly when death occurred. Fits Kaplan-Meier curves (stratified, with a log-rank test) and a Cox proportional-hazards model via tools.medical_track.kaplan_meier / cox_ph. The script's own header carries an explicit, unmissable caveat: length_of_stay is a plausible, not confirmed time-to-event proxy, and that must be confirmed with the real-data owner before this is reported as a genuine survival analysis.
    • psm.py — regression adjustment (Section 2 of infer.py) silently assumes the model's functional form is correct. Propensity-score matching and inverse-probability weighting are a differently-flawed comparison that doesn't extrapolate the same way; if both approaches tell a similar story, that's real evidence the finding isn't a modeling artifact. Ends with an E-value quantifying how strong an unmeasured confounder would have to be to explain the finding away.

    Both scripts print an explicit note that, on the independently-generated synthetic dataset, their numbers are meaningless by design — there is no real exposure-outcome relationship or real time-to-event structure for the code to recover. Verifying these scripts only ever proves the code runs; the numbers are not interpreted until the real-data run.

That's the whole medical-track loop for one project. burnout-mediation and example-survey-sem (SEM track) follow the same A→B→D shape, but Stage D calls into tools/sem_track instead of tools/medical_track — covered in full in Part III.

III

tools/ reference

Every non-trivial statistical method in this codebase lives here as an importable, independently-tested function — not copy-pasted into each project script. Project scripts (Part II) are thin: they name the variables and call into these packages.

tools.sap_gate Phase 0

A quality gate that checks whether a project's pre-registration decisions (plans/sap.md and friends) are actually recorded before any analysis script may be generated — missing-data strategy, multiplicity plan, confounder selection rule, SEM ordinal-estimator decision. The point is to make these decisions exist before a result has been seen, not to check them after the fact.

run_phase0_gate(project_dir: str | Path) -> dict[str, Any]

tools/sap_gate/gate.py. The single entry point — orchestrates four checks (missing-data, multiplicity, confounder-selection, ordinal-estimator) and returns a report dict with the exact shape the dr-output-qa-gate skill already expects: qa_status (pass / needs_revision / blocked), required_artifacts, missing_artifacts, checks, issues, next_allowed_step. Skips the confounder/estimator checks gracefully when the project's track (medical vs. SEM) makes them not-yet-applicable.

The four individual checks live in schema.py and yaml_checks.py, each returning a CheckResult (name, status, list of issue strings) that never raises on malformed input — a missing or malformed field is itself the finding, collected into issues rather than crashing the gate. sap_parser.py parses plans/sap.md deliberately loosely: it locates sections by heading text ("missing data", "multiplicity"), not by the letter in front of them, so a renumbered or hand-edited SAP still validates.

terminalbash
python -m tools.sap_gate projects/crp-mortality
# exit 0 = pass, 1 = needs_revision, 2 = blocked -- scriptable in CI

tools.diagnostics Phase 1

The shared diagnostic layer both tracks' models call. Three sub-modules:

group_tests.py — formal Table 1 comparisons

compare_continuous(data, var, group) -> GroupTestResult compare_categorical(data, var, group, min_expected=5.0) -> GroupTestResult

Neither test is fixed in advance — both branch at runtime and record why. Continuous: Shapiro-Wilk per group first; if every group passes (p ≥ 0.05), Welch's t-test (2 groups) or Welch's one-way ANOVA (>2, hand-derived below since scipy.stats.f_oneway assumes equal variances); otherwise Mann-Whitney U or Kruskal-Wallis. Categorical: chi-squared if every expected cell count clears 5, else Fisher's exact (via scipy.stats.fisher_exact, which handles r×c tables, not just 2×2).

Welch's ANOVA, hand-derived and cross-validated

_welch_anova() implements Welch (1951)'s formula directly (weighted grand mean, adjusted F statistic and denominator df) because scipy has no built-in unequal-variance one-way ANOVA. Cross-checked against R's oneway.test(var.equal = FALSE) on identical data during development: exact match to 6 decimal places (F = 7.353164, p = 0.001550, both languages).

regression_diagnostics.py — is the adjusted model trustworthy?

compute_vif(data, formula_rhs) -> pd.DataFrame

Variance inflation factor per term (patsy-encoded exactly as the model itself), flag threshold 5.0. Cross-validated against R's closed-form 1 / (1 - R²) VIF to 6 decimal places.

compute_influence(fit_result) -> (pd.DataFrame, threshold) compute_dfbetas(fit_result) -> (pd.DataFrame, threshold)

Cook's distance (threshold 4/n) and DFBETAs (threshold 2/√n) from a fitted statsmodels GLM's own influence object. DFBETAs differ a few percent from R's dfbetas() — a documented, harmless rounding difference in the one-step Newton approximation both languages use, not a bug (fitted coefficients match to 6 decimals either way).

box_tidwell_test(data, outcome, base_formula_rhs, continuous_vars) -> pd.DataFrame

Refits outcome ~ base_rhs + var:np.log(var) for each continuous variable; a significant interaction term (p < 0.05) means var is likely non-linear on the logit scale. Non-positive variables (log undefined) are reported as skipped, never silently dropped. Feeds Phase 2's nonlinear handling.

bootstrap_validation.py — Harrell's optimism correction

bootstrap_optimism(data, formula, outcome, n_boot=200, seed=2026) -> BootstrapValidationResult

For each of n_boot resamples: refit on the resample, evaluate on the resample itself ("apparent" performance) and on the original data ("test" performance). The average gap is the optimism; apparent minus optimism is the corrected estimate of real-world performance. Reports both AUC and calibration slope.

AUC is computed via the exact Mann-Whitney-U↔AUC identity (U / (n_pos × n_neg)), not an approximation — deliberately avoids adding scikit-learn as a dependency just for roc_auc_score.

tools.medical_track Phase 2

firth_logistic.py — penalized logistic regression

firth_logistic_regression(data, formula, max_iter=50, tol=1e-6) -> FirthResult

Firth's modified-score IRLS (Firth 1993; Heinze & Schemper 2002), hand-implemented — no maintained Python package exists. The core loop, in full:

tools/medical_track/firth_logistic.pypython
for iteration in range(1, max_iter + 1):
    eta = X @ beta
    pi = 1.0 / (1.0 + np.exp(-eta))
    w = pi * (1 - pi)
    xtwx_inv = np.linalg.inv(X.T @ (X * w[:, None]))

    # Hat-matrix diagonal h_i = w_i * x_i (X'WX)^-1 x_i'
    h = w * np.einsum("ij,jk,ik->i", X, xtwx_inv, X)

    # Firth's modified score: ordinary score + penalty h_i*(0.5 - pi_i)
    u_star = X.T @ (y - pi + h * (0.5 - pi))
    delta = xtwx_inv @ u_star
    # ... step-halving safety net, then convergence check on max|delta| < tol
Cross-validated against R's logistf

Two fixtures, checked during development: a well-behaved dataset (R gives Intercept=0.1054584, x1=0.9989356, x2=−0.2230824 — Python matched to 4+ decimals) and a deliberately-separated one where plain MLE's coefficient blows up to ~4.74 while Firth pulls it to a stable 2.1492432 (R and Python agreed on the corrected value too). The R port built later in this project re-verified the identical algorithm to ~1e-7 agreement against the same package.

nonlinearity.py — what to do once Box-Tidwell flags a variable

log_transform_if_skewed(x, skew_threshold=1.0) -> TransformDecision restricted_cubic_spline_basis(x, n_knots=4, knots=None) -> pd.DataFrame

First remedy: log-transform if the variable is strictly positive and its Fisher-Pearson skewness exceeds 1.0. Second remedy (implemented, available, not currently exercised by any example project's data): Harrell's restricted cubic spline basis — n_knots−2 smooth basis columns replacing a single linear term.

survival.py — time-to-event

kaplan_meier(data, time_col, event_col, group_col=None) -> KaplanMeierResult cox_ph(data, formula_rhs, time_col, event_col) -> CoxPHResult

Thin wrappers around statsmodels.duration's SurvfuncRight (Kaplan-Meier, with survdiff for the log-rank test) and PHReg (Cox proportional hazards). PHReg defaults to Breslow tie-handling, which the R mirror's coxph() does not (R defaults to Efron) — a documented, expected small difference in fitted coefficients when there are tied event times, not a bug in either language.

propensity.py — PSM, IPTW, E-value

propensity_scores(data, treatment_col, covariates_rhs) -> pd.Series psm_match(data, treatment_col, propensity, caliper=None, seed=2026) -> MatchResult iptw_weights(treatment, propensity, stabilized=True) -> pd.Series e_value(estimate, ci_bound=None, measure="OR", rare_outcome=False) -> dict

psm_match: greedy 1:1 nearest-neighbor matching without replacement, on the logit of the propensity score (matching on the raw probability compresses distances near 0 and 1, distorting "nearest"). Default caliper is 0.2 SD of the logit-PS (Austin 2011); unmatched treated units beyond the caliper are dropped, never force-matched.

e_value: VanderWeele & Ding (2017) — the minimum risk-ratio-scale association an unmeasured confounder would need with both exposure and outcome to fully explain away the observed estimate. An OR is converted to an approximate RR via √OR by default (the standard approximation for a non-rare outcome); pass measure="RR" or rare_outcome=True to skip that conversion. Validated during development: RR=2 gives E-value 3.4142, matching VanderWeele & Ding's own published worked example.

multiplicity.py — FDR control

benjamini_hochberg(p_values, alpha=0.05) -> pd.DataFrame

Thin wrapper around statsmodels.stats.multitest.multipletests. Built and tested, but not currently called from any of the four example projects — each project's SAP declares exactly one planned comparison (correction_method: none_single_comparison), so there's no live multi-comparison case yet. Wire it in if a project's SAP ever declares more than one.

tools.sem_track Phase 3

estimator.py — ordinal-aware CFA/SEM fitting

fit_measurement_model(data, constructs, estimator="DWLS", ordinal_items=None) -> FitResult fit_structural_model(data, syntax, estimator="DWLS", ordinal_items=None) -> FitResult factor_scores(fit, data) -> pd.DataFrame

Fits via semopy, declaring every Likert item ordinal: and using the DWLS objective (WLSMV in lavaan/R terms) on the polychoric correlation matrix — the methodologically correct estimator for ordinal indicators (Flora & Curran 2004), not the plain-ML default that was flagged needs_review in every project's Phase 0 plan.

.converged comes from the solver's own SolverResult.success, not from checking whether fit indices are non-NaN — semopy's SRMR is always NaN regardless of convergence, a semopy quirk that would otherwise misreport every successful fit as failed.

fit_structural_model's real limitation

With many ordinal indicators plus structural paths, semopy 2.3.11's WLS solver can stall at its starting values (chi2 comes back infinite) instead of raising an error. .converged will correctly read False here — treat that as "this model shape doesn't fit reliably with semopy's solver," not as evidence about the real structural relationship. This is exactly why mediation.py below exists as a separate, more robust path for structural models.

reliability.py & validity.py — beyond Cronbach's alpha

mcdonald_omega(loadings, error_vars) -> float average_variance_extracted(std_loadings) -> float composite_reliability(std_loadings) -> float htmt(data, construct_a_items, construct_b_items) -> float

All four are closed-form and computed from a fitted CFA's own standardized loadings — no additional model fit needed. Omega doesn't assume tau-equivalence (equal loadings) the way alpha does, which the CFA step usually contradicts. AVE is the mean squared standardized loading (≥ 0.50 is the Fornell & Larcker 1981 threshold for convergent validity). Composite reliability is numerically the same formula as omega under the standardized model — reported separately by convention, not because they're independent evidence. HTMT is computed from raw-item Pearson correlations (not the CFA's polychoric matrix) — below 0.85 (strict) or 0.90 (lenient) supports discriminant validity between two constructs.

A real bug this caught: lval/rval orientation

reliability_from_cfa()'s docstring flags this explicitly: semopy represents a loading "Construct =~ item" internally as the row item(lval) ~ Construct(rval) — the opposite of what the arrow notation suggests. Getting this backwards (filtering on lval == construct instead of rval == construct) silently returns an empty frame, not an error, and everything downstream quietly computes NaN. The same bug, in the opposite direction, was independently rediscovered while porting this logic to lavaan (R) — lavaan's own orientation is lhs=construct, rhs=item, the mirror image of semopy's.

mediation.py & model_comparison.py — structural models with real uncertainty

bootstrap_mediation(data, constructs, mediator, predictor, outcome, outcome_is_binary=True, covariates=None, estimator="DWLS", n_boot=200, seed=2026) -> MediationBootstrapResult bootstrap_structural_regression(data, constructs, outcome, predictors, ...) -> RegressionBootstrapResult compare_nested_regressions(fit_full, fit_restricted) -> RegressionComparisonResult

bootstrap_mediation is the two-step factor-score-regression approach (Skrondal & Laake 2001) described above, refit inside a bootstrap loop so the reported percentile CI on the indirect effect (a×b, a product of two coefficients — not normally distributed) reflects uncertainty from both the factor-score stage and the structural-regression stage. bootstrap_structural_regression is the same machinery for a model with parallel predictors and no mediation path (used by example-survey-sem, which has no indirect-effect term to report).

compare_nested_regressions is a plain likelihood-ratio test between two already-fitted statsmodels results, for "does this term earn its keep" questions (e.g. full vs. restricted mediation).

invariance.py — measurement invariance across groups

configural_check(data, constructs, group_col, estimator="DWLS") -> ConfiguralResult metric_invariance_bootstrap(data, constructs, group_col, estimator="DWLS", n_boot=30, seed=2026, alpha=0.05) -> pd.DataFrame

semopy has no genuine multi-group SEM — its groups= fit parameter only mean-centers each group's data before pooling into one fit; it does not estimate or constrain per-group parameters (confirmed against its own docstring during development). The workaround: fit the measurement model separately in each group (configural_check, each fit individually robust), then bootstrap each group's loadings and test whether each item's loading differs significantly between groups (metric_invariance_bootstrap, exactly 2 groups). This is more granular than the textbook omnibus chi-square test — it names which item breaks invariance, which is what you actually act on. Scalar (intercept/threshold) invariance is not implemented.

R does this natively

lavaan supports true multi-group SEM (group= + group.equal=c("loadings"), compared via a real chi-square difference test) — the semopy limitation above doesn't exist there. The R mirror of this file uses that directly rather than porting this bootstrap workaround; see burnout-mediation/scripts/sem_invariance.R's header for the full account.

tools.reporting Phase 5

Stage E (dr-05-present-results) turns real-run output into manuscript-ready tables and text. This package is the automation behind two pieces of that: pulling diagnostic numbers out of real-run CSVs, and pulling three limitation flags out of plan files — both were originally just prose instructions for an agent to follow by hand; this makes them actual, tested code.

build_diagnostics_extracted(vif_csv_text=None, bootstrap_validation_csv_text=None, firth_csv_text=None, box_tidwell_csv_text=None, bootstrap_mediation_csv_text=None, bootstrap_mediation_n_boot=None) -> dict

diagnostics_extraction.py. Every argument is real-run CSV text, never a path into the repo — real output lives in results_real/, outside the repo's own reach the same way real data always is. Parses VIF, bootstrap-validation, Firth/Box-Tidwell, and bootstrap-mediation output into one dict matching the Stage E traceability-YAML schema. The mediation sub-block derives a none / partial / full conclusion automatically from whether the indirect and direct effects' CIs exclude zero.

build_limitations_pulled_forward(sap_md_text=None, sem_plan_yaml_texts=None) -> dict

limitations_extraction.py. Unlike diagnostics, these three flags come from plan files (safe to read before any real run happens): the missing-data strategy from plans/sap.md Section H (reusing tools.sap_gate.sap_parser rather than re-deriving a second parser for the same file), any construct with exactly one item from the SEM plan YAMLs, and an always-true note that the code was verified against synthetic data first — a transparency statement about the workflow itself, not something that varies by project.

Repo-maintenance tooling Phase 6

Not statistical methods — these three keep the codebase itself honest as it grows.

tools.smoke_test.run_all(project_filter=None) -> list[ScriptResult]

Discovers every projects/*/scripts/*.py and runs each against a contract determined by its filename — not a blanket "exit 0 = pass." A Stage D script (desc.py, infer.py, ...) must exit 0. pattern_extract.py / synthesize_data.py must refuse cleanly (exit 1, a usage message, no traceback) when run with no real-data argument — that refusal is the pass condition, since these scripts must structurally never guess at real data. synthesize_data_correlated.py's template must exit 0 printing its edit-me instructions. A script name this tool doesn't recognize is reported as unknown_category, never silently marked pass or fail.

tools.parity_check.check_all(project_filter=None) -> list[ProjectParity]

Flags any scripts/ stem that exists in .py but not .R, or vice versa, per project. A flagged gap is informational, not automatically a bug — some are deliberate, scoped choices (documented per-project); this tool makes drift visible, it doesn't fix it.

tools.skills_sync_check.check_mirror(mirror, canonical=CANONICAL) -> MirrorDrift fix_mirror(mirror, canonical=CANONICAL) -> None

Skill documentation is duplicated across skills/ (canonical) and three per-agent-tool mirrors (.claude/skills/, .opencode/skill/, .agents/skills/). Unlike the R/Python asymmetry above, there's no legitimate reason for these to differ — --fix is safe to run unconditionally, it only ever re-syncs from canonical, never invents content. Both this and parity_check are wired into .pre-commit-config.yaml and .github/workflows/ci.yml, prepared but inert until the repo has a .git/ directory.

Testing

Every tools/ package has a matching tests/test_<package>.py. All seven files follow the exact same self-contained pattern — no pytest, no fixtures framework, no test discovery magic.

tests/test_*.py — the shared patternpython
_passed = 0
_failed: list[str] = []

def check(name: str, condition: bool) -> None:
    global _passed
    if condition:
        _passed += 1
    else:
        _failed.append(name)
        print(f"FAIL: {name}")

# ... every assertion in the file is check("description of what should be true", condition) ...

print(f"\n{_passed} passed, {len(_failed)} failed")
if _failed:
    sys.exit(1)
print("ALL TESTS PASSED")

Run any single file directly — there's no runner to invoke:

terminalbash
.venv/bin/python tests/test_medical_track.py
.venv/bin/python tests/test_sem_track.py

# the whole suite, one file at a time:
for f in tests/test_*.py; do .venv/bin/python "$f"; done

What each test file actually checks

Not just "does it run" — every test file that wraps a real statistical method cross-validates it against a known-correct source, hardcoded as an expected value in a comment explaining where it came from:

Test fileCross-validated against
test_diagnostics.pyWelch's ANOVA vs. R's oneway.test(var.equal=FALSE) (exact match to 6dp); VIF and Box-Tidwell vs. closed-form R equivalents
test_medical_track.pyFirth regression vs. R's logistf on a well-behaved and a deliberately-separated dataset; E-value vs. VanderWeele & Ding's own published worked example (RR=2 → E-value 3.4142)

A real trap: shared output directories between languages

test_reporting.py originally read live files from projects/*/outputs_synthetic/ as fixtures. Every project's outputs_synthetic/ is shared between its .R and .py scripts by design — running the R version overwrites exactly the file the Python version just wrote, and vice versa. A test that reads the live file flakes depending on which language last ran, not on whether the extraction code is correct. Fixed by freezing a verbatim snapshot of real Python-generated output as an inline string constant in the test file itself. If you ever add a test that reads from outputs_synthetic/, freeze it instead.

VI

Extending the codebase

Conventions to follow so new code fits the existing shape.

Starting a new project

  1. Copy the template

    cp -r projects/_template projects/my-new-project. It has the standard sub-folders (pattern/, data_synthetic/, outputs_synthetic/, plans/, results_real/, scripts/) but no scripts yet.

  2. Run Stages A–C locally (real data, your own machine)

    Copy py-scripts/pattern_extract.py and synthesize_data.py into scripts/, run them against your real file, review the pattern output, generate the synthetic dataset.

  3. Copy Stage D from py-scripts/, or from the nearest existing project

    Both are current with Phases 1–3 (Part IV). py-scripts/infer.py or sem_measurement.py ship with placeholder variable/construct names to rename; a project's own scripts (e.g. crp-mortality/scripts/infer.py) come pre-filled with a real example's names, which can be a faster starting point when your new project's shape closely matches an existing one.

  4. Fill in Phase 0 pre-registration before running Stage D

    plans/sap.md Section H (missing-data strategy) and Section I (multiplicity), plus plans/confounding_adjustment_plan.yaml or plans/sem_measurement_plan.yaml depending on track. Run python -m tools.sap_gate projects/my-new-project — it should report pass before you generate analysis code.

  5. Verify, then check parity

    python -m tools.smoke_test --project my-new-project once your Python scripts exist. If you're maintaining an R mirror too, python -m tools.parity_check will flag any script that exists in one language but not the other.

Adding a new statistical method to tools/

Conventions observed consistently across every existing module — follow them so new code doesn't stand out:

  • A result is a @dataclass, not a raw dict or tuple. Every function that returns more than one related number returns a dataclass (FirthResult, GroupTestResult, BootstrapValidationResult, ...), usually with a to_frame() or to_row()/to_dict() method for the CSV-writing project scripts to call.
  • Never raise on malformed or missing input inside a check function (the tools.sap_gate and tools.reporting convention). A missing field, an empty CSV, a None input is itself the finding — collect it into an issues list or set available=False, don't crash the caller's script over it. Reserve real exceptions for genuine programming errors (wrong type, contract violation), not for "the data doesn't have this yet."
  • Document what you validated against, in the module docstring, not just in your head. Every non-trivial algorithm in this codebase (Firth, Welch's ANOVA, E-value, the lval/rval orientation) has a paragraph explaining what reference source it was checked against and what the result was. That paragraph is often the only thing standing between a subtle bug and a confident-looking wrong number.
  • If a library has a known limitation, say so in the docstring, with a specific description of the failure mode — not a vague "may not always work." tools/sem_track's modules are the clearest examples: semopy's SRMR-always-NaN, its fake multi-group support, its WLS solver stalling on large ordinal structural models are each described precisely enough that the next person doesn't have to rediscover them by debugging from scratch.
  • Write the test file alongside the code, in the same self-contained check() pattern as Part V, and cross-validate against a real external source wherever one exists (R's base functions, a published worked example, a hand-computable small fixture) rather than only testing "the function returns something."

If you're also maintaining the R mirror

Two rules, both enforced by tooling, not just convention:

  • Base R only, with two named exceptions: lavaan (SEM) and survival (Cox/Kaplan-Meier) — both "recommended"-tier packages that ship with every R installation and never need install.packages(). Anything else implementable in base R stays in base R, even when a package exists for it — Firth's algorithm is hand-implemented in both languages for exactly this reason, cross-validated against the package that would have provided it (logistf) rather than depending on it.
  • Run python -m tools.parity_check after adding or renaming any script. It flags a .py file with no .R counterpart (or vice versa) per project — a flag is a prompt to either port it or note in the file's own header why it's deliberately one-language-only (matching how burnout-mediation/scripts/sem_invariance.py's header explains the semopy limitation that makes its R counterpart methodologically different, not just translated).
